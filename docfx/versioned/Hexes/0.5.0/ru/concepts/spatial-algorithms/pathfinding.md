# Поиск пути

Akeldov.Math.Hexes ищет маршрут с минимальной стоимостью по конечной прямоугольной карте гексов.
Поиск использует алгоритм Дейкстры, следует только через соседей с общим ребром и поддерживает
разные стоимости движения в противоположных направлениях.

## Граф гексагональной карты

<xref:Akeldov.Math.Hexes.HexMapTopology> определяет вершины и рёбра графа:

- каждый допустимый `VectorXYInt` — одна вершина;
- у внутреннего гекса не более шести исходящих переходов;
- раскладка определяет индексы шести соседей;
- переходы за пределы разрешения карты не создаются.

Радиус гекса, начало координат и физическое расстояние между центрами в поиске не участвуют.
Две геометрически по-разному размещённые карты с одинаковой топологией и одинаковыми
стоимостями дадут один и тот же результат.

## Стоимость перехода

<xref:Akeldov.Math.Hexes.Pathfinding.HexTransferCostMap> объединяет две реализации
`IHexMap<float>` с одинаковой топологией:

- `ExitCosts[from]` — цена выхода из исходной ячейки;
- `EntryCosts[to]` — цена входа в следующую ячейку.

Стоимость одного направленного шага вычисляется так:

```text
cost(from → to) = ExitCosts[from] + EntryCosts[to]
```

Поэтому переходы `A → B` и `B → A` могут стоить по-разному. В полную стоимость маршрута не
входит цена входа в начальный гекс и цена выхода из конечного: учитываются только реально
выполненные шаги.

`GetTransferCost(from, to)` возвращает эту сумму для любых двух индексов внутри топологии. Сам
метод не проверяет соседство и не добавляет расстояние. Ограничение переходов шестью соседями
применяет `FindShortestPath`.

Объект стоимости удерживает переданные карты, а не создаёт их снимок. Если изменяемая исходная
карта получает новые значения, следующий поиск использует эти значения.

## Допустимые значения и препятствия

Все конечные стоимости должны быть неотрицательными. `float.NaN`, отрицательные значения и
`float.NegativeInfinity` приводят к `InvalidOperationException`. Перед началом каждого поиска
проверяются обе карты целиком, в том числе при совпадающих начальном и конечном индексах.

`float.PositiveInfinity` — допустимое специальное значение:

| Где задана бесконечность | Следствие |
|---|---|
| В `EntryCosts[index]` | В гекс нельзя войти из соседней ячейки |
| В `ExitCosts[index]` | Из гекса нельзя выйти в соседнюю ячейку |
| В обеих картах | Гекс полностью отделён от остальных ячеек |

Такое разделение позволяет моделировать односторонние ограничения. Например, бесконечная цена
входа не мешает начать маршрут в этой ячейке, а бесконечная цена выхода из цели не мешает
завершить маршрут в ней.

## Пример поиска

В следующем примере прямой маршрут проходит через дорогую верхнюю ячейку. Алгоритм выбирает более
длинный, но дешёвый обход по нижнему ряду.

```csharp
using Akeldov.Math.Hexes;
using Akeldov.Math.Hexes.Pathfinding;
using Akeldov.Math.Spatial2D;

var topology = new HexMapTopology(
    width: 3,
    height: 2,
    layout: Layout.OddR);

var exitCosts = new HexMap<float>(topology, new[]
{
    1f, 100f, 1f,
    1f,   1f, 1f
});

var entryCosts = new HexMap<float>(topology, new[]
{
    1f, 100f, 1f,
    1f,   1f, 1f
});

var costs = new HexTransferCostMap(exitCosts, entryCosts);

HexPath? path = costs.FindShortestPath(
    from: new VectorXYInt(0, 0),
    to: new VectorXYInt(2, 0));
```

Полученный путь проходит через индексы `(0, 0)`, `(0, 1)`, `(1, 1)`, `(2, 0)`. Каждый из трёх
шагов стоит `1 + 1`, поэтому `TotalCost` равен `6`. Два шага по верхнему ряду стоили бы `202`.

## Результат поиска

`FindShortestPath` возвращает <xref:Akeldov.Math.Hexes.Pathfinding.HexPath> либо `null`:

- `HexIndexes` — доступная только для чтения последовательность от начального индекса до
  конечного включительно;
- `TotalCost` — сумма стоимостей переходов между соседними элементами последовательности;
- `null` означает, что конечный индекс нельзя достичь через конечные по стоимости переходы.

Если `from == to`, успешный результат содержит единственный индекс и имеет нулевую стоимость.
Когда существует несколько маршрутов с одинаковой минимальной стоимостью, используйте
`TotalCost` как гарантируемый критерий и не связывайте логику приложения с выбором конкретной
равноценной последовательности.

Индексы `from` и `to` должны входить в топологию. Несовпадающие топологии карт стоимости
отклоняются при создании `HexTransferCostMap`, а индексы вне карты — при вызове поиска.

Вернитесь к [обзору пространственных алгоритмов](index.md) или переходите к
[разбиению пространства](space-partitioning.md), если ячейки нужно классифицировать по мировому
положению, а не соединять маршрутом.
